# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`verikun` (CLI binaries `verikun` and `vk`) drives a connected Android device/emulator or iOS simulator/device — like Puppeteer drives a browser: tap, type, swipe, screenshot, and **inspect the UI hierarchy by semantic identifiers**. It is built to be invoked by AI agents, so its output and exit codes are a deliberate machine contract, not just human ergonomics.

## Commands

```sh
npm install        # dev deps (typescript, @types/node); NO runtime deps — also builds dist/ via the prepare hook
npm run build      # tsc: src/ -> dist/
npm run dev        # tsc --watch
npm test           # type-check + run the unit suite (node:test) — see Unit tests below
npm link           # optional: put `verikun` + `vk` on PATH (else: node dist/bin/verikun.js <cmd>)
```

**No linter is configured;** TypeScript `strict` is the only static gate (`npm run build` or `npx tsc --noEmit`). `npm test` is the device-free unit suite — scope and conventions under *Unit tests*. End-to-end behaviour is verified by running the built CLI against a real device (`vk doctor`, `vk ui`, …), which may be a personal phone: no destructive actions (submitting forms, creating accounts).

`dist/` is gitignored: rebuild after editing `src/**`, or the linked `vk` / `node dist/...` is stale.

## Versioning, changelog & docs

The version is declared once, in `package.json`. `src/version.ts` (`VERSION` — the `vk --version` banner **and** the plan-cache `COMPILER_FINGERPRINT`) and `.claude-plugin/plugin.json`'s version are **generated at build** by `scripts/gen-version.mjs`: never hand-edit them; `tests/version.test.ts` fails on drift.

Any behaviour change — a command, flag, selector rule, exit code, report format, `device set` key, platform capability, or the `vk ai` grammar/IR — has **three inseparable consequences**:

1. **Bump `package.json`'s version** (semver: patch for a fix, minor for a capability, major for a broken contract). The rebuild rotates `COMPILER_FINGERPRINT`, so every cached `vk ai` plan recompiles — intended.
2. **Add a `CHANGELOG.md` line** under `## [Unreleased]`: one line per change, ≤ 25 words, leading with the command or flag. Style, and where the rationale goes instead: `.claude/skills/changelog-entry/SKILL.md`.
3. **Update every doc that owns the contract, in the same commit** — `SKILL.md`, `README.md` where it is mentioned, and the `docs/` page(s) in the *Which page owns which contract* table under *Documentation site*. The two most often missed: **`reference/commands.md`** for any command or flag, and **`guides/platform-support.md`** for anything a platform does differently.

Verify with `npm run docs:build` (Node ≥ 22.12 — `nvm use 22` first; CI runs 20.x). It fails on a dead internal link, the docs' only automated check.

**A docs-only change** — fixing prose, adding a page, restructuring the site — bumps nothing and needs no version change, but still takes a `## [Unreleased]` entry. Say `No version bump: no CLI behaviour changed.` in the commit body, as commit `76c2f85` does.

### Releasing to npm

`verikun` is published to npm by **pushing a tag** (`.github/workflows/publish.yml`). In the release PR: bump `package.json`'s `version`, `npm run build` (regenerates `version.ts` and `plugin.json`), rename `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`, and eyeball `npm pack --dry-run`. Once merged:

```sh
git tag v0.10.0 && git push origin v0.10.0
```

**Tag a commit that contains `publish.yml`.** A tag-push event runs the workflow *as of the tagged commit*, so tagging anything older than the commit that added the workflow does nothing at all — no run, no error, nowhere to look.

The workflow refuses a tag that disagrees with `package.json`'s version, re-checks the generated files, runs the unit suite, then publishes with **provenance**. A prerelease tag (`v1.0.0-rc.1`) goes out under the `next` dist-tag and takes the notes of the release it is a candidate for. The GitHub release is a **separate job**: if only it failed, re-run it or create the release by hand — never re-push the tag.

Auth is npm **trusted publishing** (OIDC); there is no token to rotate. npm's per-package config names the workflow **by filename**, so renaming or moving `publish.yml` breaks publishing at publish time and nothing sooner — rename it and update the trusted-publishing config at `npmjs.com/package/verikun/access` together.

## Architecture

Three layers, separated so two of them never touch a platform:

```
bin/verikun.ts → cli.ts ─┬─ ui/selector.ts   match @id / text: / desc: / class:  (platform-agnostic)
   (dispatch)            ├─ ui/format.ts      inline / compact / tree / json rendering (platform-agnostic)
                         ├─ device/settings.ts  device-setting capability table (platform-agnostic)
                         └─ drivers/ ─→ adb | xcrun     the ONLY platform-specific code
                                  │
                                  └─ produces normalized Element[]  (ui/android-parse.ts for Android)
```

- **`src/types.ts` is the seam.** The `Driver` interface is what every platform backend implements, and `Element` is the normalized node model every other layer consumes. `cli.ts`, `ui/selector.ts`, and `ui/format.ts` operate **only** on `Element[]` and `Driver` — they contain zero `adb`/`xcrun` knowledge. Keep it that way: platform quirks belong in `drivers/`.
- **`getDriver(platform, device)` (`drivers/index.ts`)** is the only place a concrete driver is constructed (except `commands/devices.ts`, which probes both backends directly to list everything attached).
- **`cli.ts`** is the dispatcher: `run(argv)` parses args and builds a `Ctx { driver, platform, device, positionals, flags, record? }` (`commands/context.ts`); `executeCommand(command, ctx)` is the `switch` to each `cmdX(ctx)` handler. Helpers and handlers that outgrow the dispatcher live under **`src/commands/`** (`auto-wait.ts`, `batch.ts`, `devices.ts`), which never import `cli.ts` (`auto-wait.ts` takes `Ctx` from `commands/context.ts`). **Adding a command is five edits, not one:** a `case` (+ any aliases); a line in `usageText()`; a row in `docs/…/reference/commands.md`; a row in `docs/…/guides/platform-support.md` (every command is in that matrix — if it behaves identically everywhere, say so with four ✅, don't omit it); and, if it should appear in a test run, an entry in `RECORDABLE` in `run.ts`. A command that reaches `usageText()` but not the docs is invisible to every user who did not read the source.
- **`server-pool.ts` + `server-worker.ts`** sit beside `server.ts`: the pool is mechanism (a worker thread per device, replies correlated, one command at a time per device), the server keeps the policy — leases, auth, the grammar gate, and which device failover moves to. See *Parallel `vk suite` and the `vk server` device pool* and *Server device failover*. Two more siblings hold what is neither: `server-http.ts` (the transport helpers — `HttpError`, capped body reads, JSON replies, wire encodings) and `server-lifecycle.ts` (the start/stop/restart seam `buildServer` is injected with, plus its production implementation).
- **`run.ts` + `report.ts`** sit beside `cli.ts` (they may use the driver, like `cli.ts` does — they are not part of the platform-agnostic core). `run.ts` records each recordable command into an on-disk test run; `report.ts` is pure (`RunState → JUnit/HTML` strings, no fs, no driver). See *Test runs* below.
- **`device/settings.ts` is a table, not code.** It declares every `vk device set` key: its value domain, its per-platform support (`supported` / `unsupported` / `noop`), and — where unsupported — the **manual equivalent**. One table drives four consumers: argument validation, the driver switch, `vk device caps`, and the `vk ai` plan validator. Adding a setting is a table row plus a `case` in each driver, **plus a row in `reference/device-state.md` and in `guides/platform-support.md`'s device-settings matrix**; a platform gap can never be documented in one place and forgotten in another. Two invariants the unit suite enforces: every `unsupported` entry names a manual equivalent, and every `noop` says why it was unnecessary. See *Device settings* below.

Every command re-captures the hierarchy fresh (`driver.getElements()` → `uiautomator dump`); nothing is cached between invocations. This is intentional (the screen may animate/auto-advance between calls) — don't add a snapshot cache expecting staleness to be acceptable.

## Cross-cutting contracts (the reason agents can drive this)

These conventions span files; breaking one quietly breaks agent control flow.

- **Exit codes are an API.** `0` ok · `1` not found / assertion failed / wait timeout · `2` usage error, **ambiguous selector**, or a device another job holds · `3` environment error (tool missing, no usable device, dump/screencap failed). They are carried by `CliError(message, exitCode)` (`src/errors.ts`) and thrown from anywhere; the single `try/catch` in `run()` is the *only* place that maps an error to a process exit code. A non-`CliError` throw becomes exit `3`. When you add logic, throw `CliError` with the right code rather than printing-and-returning.
- **stdout = data, stderr = diagnostics.** `out()` → stdout, `err()` → stderr (`src/output.ts`). Healed-match notes, "tapped …" confirmations, and warnings go to stderr so stdout stays parseable.
- **`--json` everywhere, including errors.** When `--json` is set, the catch in `run()` emits `{error, exitCode}` as JSON. New commands should honor `--json` for their success output too.
- **No host shell, ever.** `exec.ts` runs everything via `spawnSync` with an args array (no `shell: true`) — so host-side injection is impossible. *Device-side* shell escaping (for `adb shell input text …`) is the driver's job: see `escapeText()` in `drivers/adb.ts` (allowlist: backslash-escape **all** ASCII punctuation, leave alphanumerics/non-ASCII alone, then ` ` → `%s`). Add new device-shell args through that, not by string-concatenating into a command.
- **Zero runtime dependencies is a design constraint.** The XML parser (`ui/android-parse.ts`), arg parser (`args.ts`), and PNG downscaler (`image.ts`, decode/box-resample/encode over `node:zlib` only) are hand-rolled on purpose. Don't add an npm runtime dep without a deliberate decision — reach for a Node builtin first.

## Selector auto-healing (`ui/selector.ts`)

Matching is always case-insensitive and tries progressively looser **tiers**, stopping at the first that yields any match: `exact` → `partial` (substring) → `normalized` (strip case + all punctuation/whitespace/emoji). So `text:sign up`, `text:SIGN UP`, `text:signup` all find a "Sign up" button. `--contains` drops the `exact` tier; `--index N` picks the Nth within the winning tier.

Ambiguity is **never** auto-resolved: `resolveOne()` throws `CliError(…, 2)` listing the candidates when the winning tier has >1 match and no `--index` — actions never tap a guess. A healed (non-`exact`) match is noted on stderr by `cli.ts`'s `healNote()` so the caller can tighten the selector.

**State modifiers** (`STATE_ATTRS` = `enabled`/`selected`/`checked`/`focused`) narrow the candidate pool *before* the tier ladder and are **tri-state** on `Selector` (unset / `true` / `false`) — so `stateFromFlags()` must leave an absent flag `undefined`, never `false`, or every selector silently gains "must be disabled, unselected, unchecked and unfocused". `--x`/`--not-x` together is exit 2. Each predicate is exactly one attribute: never strengthen one with a conjunct the platform reports unreliably (see the comment on `filterByState`).

A modifier may also be appended to the selector string (`id:btn --not-selected`, stripped by `splitStateModifiers()`) — the form a `vk ai` control node's bare `selector: string` needs. `Selector.raw` keeps the original for errors and reports.

`ui/state-support.ts` refuses a modifier the platform cannot report (exit 3 — `idb` emits no `selected`/`focused` at all, see `IOS_UNREPORTED_STATE`), gated in `buildSelector` and in the engine's `present()`/`execRead()` via `EngineDeps.platform`: a filter that can only ever match nothing is exactly the false signal these modifiers exist to prevent.

## Selector auto-wait (`commands/auto-wait.ts`)

Matching is a pure function of one snapshot; **waiting is layered on top in `commands/auto-wait.ts`, never in `selector.ts`** (keep `ui/selector.ts` time-free). Selector-resolving handlers (`tap`/`text`/`find`/`assert`/`swipe --on`) go through `resolveOneWaiting()` (one element) or `matchWaiting()` (a set), which re-capture and re-match every `--interval` (default 300ms) until a hit or the window elapses. `waitWindowMs(flags)`: `--no-wait`/`--wait 0` → 0 (single shot), `--wait <dur>` (bare ms, or `5s`/`800ms` via `parseDuration()`), else **5000ms** — so every selector lookup auto-waits ~5s unless opted out.

Load-bearing rules, mirroring auto-healing:
- **Only an empty match set is retried.** A present-but-plural match is surfaced *immediately* via `resolveOne()` (exit 2) — waiting can't disambiguate, and the elements are already there. `resolveOneWaiting()` only loops while there are zero matches.
- **Bare-index `tap N` and `tap --at x,y` never wait** — an index refers to a specific prior `ui` dump, so polling (which re-captures, shifting indices) would be wrong.
- **`assert` polls the whole predicate**, not just presence: `evalAssert()` is re-run each interval, so `assert --gone` waits for *disappearance* and `--text` waits for the text to match.
- Handlers that wait return `waitedMs`; `waitNote()` appends ` (waited 1.2s)` to the confirmation. The recorded step's `durationMs` already includes the wait, so the report reflects it with no extra plumbing.

Route a new selector-resolving command through these helpers (never a raw `resolveOne`/`matchElements`) so it inherits auto-wait. The `wait` *command* is unrelated: the explicit blocking poll, with its own `--timeout`/`--interval` and `--gone`.

## Auto scroll-into-view (`ui/viewport.ts` + `cli.ts`)

Same shape as auto-wait, one layer further: the geometry is pure (`ui/viewport.ts` — no device, no time), the orchestration lives in `cli.ts` (`resolveTappable()`), and `ui/selector.ts` is untouched. **Matching does not change** — an out-of-view element still matches and `vk ui` still lists it (marked `offscreen`); only *actions* (`tap`/`text`) move the screen. Inspection never has a side effect.

An element's `center` is not always a point that reaches it, and a tap on the wrong point still reports success. Two causes, both handled:
- **Cut off by its container.** `clipRegion()` finds the nearest `scrollable` ancestor (intersected with the screen); the element must sit fully inside *that*, not merely on screen.
- **Covered by something painted later.** `isOccluded()` uses document order. Inside a scroll container the target is scrolled to the container's **middle** (`scrollPlan(..., {centre:true})`); outside one, `reachablePoint()` picks another point on the element.

Rules: swipes are paced by distance (`swipeDurationMs`, ~0.75 px/ms — a fast swipe flings past the target); Android's dumper already drops invisible nodes, so `Element.offscreen` is mostly an iOS signal; every unknown (no `driver.viewport()`, an older server) degrades to "visible", which is why `Element.offscreen` is optional **and negative** (absent = visible). Refusing to act is reserved for an element with **no** on-screen pixel (`SelectorNotFoundError`, exit 1, so `vk ai` can repair or give up) — occlusion only ever warns. The measured numbers behind the pacing: `internals/contracts.md`, *Auto-scroll: measured constants*.

## Screenshot downscaling (`image.ts`)

An agent reading a screenshot pays tokens for its pixel **area**, so `cmdScreenshot` runs the capture through `downscalePng(buf, maxEdge)` (`image.ts` — pure image math over `node:zlib`, platform-agnostic and dependency-free, like `ui/*`). Cap precedence: `--full` (no resampling) > `--max <px>` > `--more` (1400px) > `VERIKUN_SHOT_MAX_EDGE` > the 700px default. Load-bearing: only 8-bit non-interlaced gray/RGB/gray-alpha/RGBA is handled — **any other PNG is returned untouched with a `reason`**, never corrupted — and it never upscales. Failure-evidence captures in `run.ts` stay full-resolution (humans read those in the report): route only agent-facing screenshots through it.

## Test runs (recording → JUnit/HTML)

Recordable commands (the `RECORDABLE` set in `run.ts` — actions + `wait`/`assert`, **not** inspection like `ui`/`find`/`devices`; `log` is the exception, so its capture lands in the report) are wrapped in `run()`: `Recorder.beginStep(...)` opens a step, the handler runs, `finish(code)` / `finishError(e)` closes it. Each `vk` call is its own process, so run state is persisted to disk and reloaded per command:

```
./.verikun/run/            active run (run.json + artifacts/)   — auto-created on first action
./.verikun/run-<lane>/     active run of ONE LANE of a parallel suite (VERIKUN_LANE)
./.verikun/runs/<id>/      archived runs (report.xml, report.html, run.json, artifacts/)
```

Key behaviours, each load-bearing:

- **Implicit start.** If no run is active, the first recordable command auto-starts one (`implicit: true`) and prints a one-time note to stderr. `vk run start` makes one explicitly and **refuses to clobber** a non-empty active run without `--force`.
- **Context rollover.** `rolloverReason()` checks the active run against the current context before each step; on a mismatch the old run is *sealed* (archived, never discarded) and a fresh one starts. Triggers: a device serial or session (`VERIKUN_SESSION`/`TERM_SESSION_ID`) change for any run; idle beyond `VERIKUN_RUN_IDLE_MIN` (default 30) for *implicit* runs only. `Recorder.seal()` is the shared finalize-and-move.
- **Step = testcase.** Each step records timing, exit code and pass/fail. Handlers enrich it via `ctx.record?.note({ selector, tier, element, message })` — how the **resolved identifier** reaches the report. Add a `note(...)` to every new selector-resolving handler.
- **Failure evidence.** A non-zero step best-effort captures a screenshot + hierarchy (`Recorder.capture`); `screenshot` steps attach their PNG. Device logs are pulled **at archive time** into `artifacts/logcat.txt`, scoped to the run's `logStart` device-clock marker when available (`vk log` uses the same window; precedence in the pure `chooseLogOpts`: `--since` > `-n` > `--full` > session > last-N). `--no-logs`/`VERIKUN_NO_LOGS` skips it on green runs; failed runs always capture. Logs are raw device output — **not redacted**. Over `--server`, `/v1/exec` returns `logStart` and `/v1/logs` serves the dump.
- **Pass/fail mapping.** Returned exit code or thrown `CliError.exitCode`: `0`→passed, `1`→`<failure>` (assertion), `≥2`→`<error>` (env/usage). `vk run archive` itself **exits non-zero when the run had failures**, so the archive command doubles as a CI gate.
- **A failed run can never archive green.** An engine-level `vk ai` failure (a give-up, a budget/timeout abort) appends **one** synthetic red step via `Recorder.recordTerminalFailure` — only when no step is already red — and `cli.ts`'s `terminalFailure()` both builds that record and prints the `[ai] …` verdict, so archive and console cannot disagree; `report.ts`'s `runFailure()` trusts `failure` over the tally. The three layers and the bug behind them: `internals/contracts.md`, *A failed run can never archive green*.
- **One active run PER LANE.** `activeDir()` is `./.verikun/run/`, or `run-<lane>` under `VERIKUN_LANE`, because every suite test starts its run with `force=true` (an `rmSync` of the active directory). Archives stay in the shared `./.verikun/runs/<id>/`, with the lane in `runId()` and each directory claimed by an exclusive `mkdirSync`. Why: `internals/contracts.md`, *One active run per lane*.
- **Secrets.** Step names never include typed text; `cmdText` redacts the value into the step message when the field `password` flag is set. Keep that property if you add input commands.
- **Disable** with `VERIKUN_NO_RUN=1` (`beginStep` returns null → `ctx.record` undefined → every `note`/`attachImage`/`attachLog` is a no-op).

## The `vk ai` agent runner (`src/agent/`)

`vk ai <file>` runs a natural-language test by treating an LLM as a **compiler, not a runtime**: compile the prose into a deterministic plan IR **once**, replay it model-free, and wake the model only to *repair* a step whose selector stops resolving. That is the cost model — a green suite costs ~$0 in tokens; you pay only on first compile and on a genuine repair, and a green run persists the repaired plan. New code lives in `src/agent/`; the rest of the CLI is reused, not reinvented.

- **`ir.ts`** — the plan IR: uniform typed nodes (a `command` leaf, or an `if-present` / `repeat` control node), **shallow** (control bodies hold leaves only, no nesting) so the structured-output JSON schema (`PLAN_JSON_SCHEMA`) stays non-recursive (the API rejects recursive schemas). `validateNode` is the grammar gate applied to both compile output **and** every model repair — a hallucinated command is rejected, never run.
- **`engine.ts`** — `runPlan(plan, deps)`: a dependency-injected interpreter (imports no `cli.ts`, so no cycle, and unit-tested with a fake `exec`). Load-bearing rule: a selector **miss** (`SelectorNotFoundError`, exit 1) or **ambiguity** (`AmbiguousSelectorError`, exit 2) heals via the model; an `assert` failure (which *returns* exit 1, never throws) is **terminal and never healed** — healing it would mask a real regression. **A repair is a decision, not a forced substitution**: the model returns a replacement leaf *or* `give_up` (`replaceStep: null`) when the live screen has no element serving the failed step's intent (the flow drifted to the wrong screen/app). A `give_up` is **terminal** — without it, a "too kind" fallback tap onto an unrelated screen would pass as a false green (`REPAIR_DECISION_JSON_SCHEMA` + the strict `REPAIR_GRAMMAR` enforce this). Loops carry a hard cap **and** a structural (sorted id+text) no-progress early-exit; the raw hierarchy is not hashed (its node order is nondeterministic).
- **`provider.ts`** — the `AgentProvider` seam, with **four** backends behind it, chosen by `providerFor(model)` (`cost.ts`) from the `--model` name alone (there is no `--provider` flag). Two are HTTP + an API key, both over Node's built-in `fetch` (no SDK, honoring zero-dep) with structured output, a cached grammar prefix and 429/5xx backoff: **`claude.ts`** (Anthropic Messages API) and **`openai.ts`** (Chat Completions; its `toStrictSchema` adapts the shared `ir.ts` schema to OpenAI's strict Structured Outputs dialect). Two shell out to an already-logged-in coding-agent CLI so the user needs **no API key at all** — both served by the single spec-parameterized **`cli-provider.ts`**: `codex-cli` (`CODEX_SPEC`) and `cursor-cli` (`CURSOR_SPEC`). Adding another CLI agent is a new `CliAgentSpec` + a `MODELS` row + a `CLI_SPECS` entry in `cli.ts`, not a new class. A CLI backend is billed to the user's subscription, so it reports empty `usage` (cost `$0`, `--max-cost-usd`/`--cost-override` inert); it runs read-only in a neutral temp dir and, lacking a native schema flag (cursor) or not, is still gated by `parsePlan`/`validateNode` like every other provider.
- **`cost.ts`** — the per-1M price table (+ `--cost-override`) and the `CostTracker` budget that aborts a run on `--max-cost-usd`. **`cache.ts`** — the plan cache keyed by NL+package+build (tolerant read → miss, atomic write, caches the compile immediately so an unchanged test never recompiles + re-persists the healed plan on green, seed-from-prior-build) and gated by a **compiler fingerprint** (`COMPILER_FINGERPRINT` = verikun version + `GRAMMAR`/`REPAIR_GRAMMAR`) recorded on each entry — `readPlan` treats a fingerprint mismatch as a miss, so updating verikun (a version bump *or* any grammar/repair-prompt edit) recompiles instead of replaying a plan the old compiler produced; `findSeed` ignores the fingerprint (an older plan is still a fine seed). **`plan-lock.ts`** — the per-key compile lock beside it (see *The plan-compile lock*). **`grammar.ts`** — the compact command grammar handed to the model; mirrors `SKILL.md` (keep in sync). **`lint.ts`** — the compile-fidelity lint (see *A compile has to cover its test*).
- **A COMPILE HAS TO COVER ITS TEST, and a plan that does not is NEVER CACHED** (`lint.ts`, off with `VERIKUN_NO_COMPILE_CHECK=1`). Every other compiler failure surfaces as a *failing* run; a truncated one surfaces as a **pass** — the short plan asserts nothing, so it fails nothing, and `cachePlan` then makes that pass replay against every later build (issue #127). Two rules — a **length floor** (plan nodes vs prose instruction units, at 0.35) and a **tail-anchor** check — both ordinary `LintFinding`s, so they buy the same one guided recompile as the other rules; only a plan that trips one *twice* is rejected. Exit **1**, deliberately not `2` (`vk suite` never retries a usage error) and not `3` (a lane reads that as an environment failure and may retire a healthy phone for a model-side problem). The same check also withholds a SEGMENT that fails it (a fragment is keyed on its own text, so a short one shortens every test that includes it) and discards a `findSeed` result that fails it (`findSeed` ignores the fingerprint, so a truncated seed outlives the bump that invalidated its own entry). Keep the counters biased to UNDERCOUNT the prose: an undercount only weakens detection, an overcount rejects a correct test. `tests/agent-lint.test.ts` pins the floor against this repo's own `example/*.md`; keep that case.

The seam into the existing CLI is **`executeOutcome`** in `cli.ts` — the recordable-command core split out of `executeParsed`, returning `{code, error}` (the error *not* mapped) so the engine can tell a heal trigger from a terminal failure. Action handlers stay **untouched**: the resolved element they record via `note()` is enough. `cmdAi` builds one shared driver + one explicit `Recorder.start` run and injects `executeOutcome` (bound to that driver) as the engine's `exec`; per-step `out()` is suppressed via `setOutputQuiet` so stdout stays the one final result while progress streams to stderr (CI liveness). **Before trusting seeding / shallow-IR depth, run the validation gate in the design doc** (hand-write the flakiest flow's plan, measure step-survival across two builds).

## The plan-compile lock (`src/agent/plan-lock.ts`)

`@include`'s promise is that a preamble shared by nine tests is compiled **once**. That held only for a *serial* suite: a pooled `vk suite` is one child `vk ai` process per test and a child inherits the cwd, so on a cold cache all N missed the same fragment in the same instant and all N called the model (issue #117). The cost is the smaller half — the real damage is N *different* nondeterministic draws of one preamble alive in one suite run, each lane running its own while `renameSync`'s last-writer-wins decides which one later tests replay. A per-key lock (`./.verikun/plan-locks/<planKey>.lock`) makes the first process compile and the rest wait and re-read.

- **BESIDE the cache, never inside it.** `.verikun/plans` is the path our own docs and `.github/workflows/suite.yml` tell users to restore with `actions/cache`; a lock packed into that tarball comes back on a fresh runner as a foreign-host corpse, on exactly the cold-cache run this exists to make cheap. It also keeps `rm -rf .verikun/plan-locks` from being one keystroke from deleting the cache. (`findSeed` filtering non-`.json` would *also* have made it safe inside `plans/` — that is not the reason, and writing it down as the reason would get the directory "simplified" later.)
- **Taken ONLY on a miss**, so the steady state — all cache hits — does zero lock I/O. `tests/agent-segment-compile.test.ts` pins that the directory is never even created on a warm run.
- **The wait ceiling is DERIVED from `--timeout`** (`planLockWaitMs`, a quarter, capped at 240s ≥ `CliProvider`'s 180s). `runAiTest` computes `deadline = Date.now() + opts.timeoutMs` *before* `obtainPlan`, so every second waited is a second the engine no longer has; a generous fixed wait would turn a healthy suite into `run timeout (900s) reached` — a new way to fail, which is the one thing this may not add. Same shape, same reason, as `claimHeartbeatMs` deriving from `claimTtlMs`.
- **Two ceilings, not one.** How long a lock is *trusted* (`LOCK_TRUST_MAX_MS`, 15m) must exceed the longest legitimate compile — Claude is 120s × 5 attempts plus backoff plus a honoured `Retry-After` — while how long we *wait* must be short. Collapsing them would make the staleness rule dead code.
- **Liveness is the pid, with an age ceiling**, and there is no heartbeat because there cannot be one: a CLI provider compiles inside a blocking `spawnSync`, so a timer in the holder never fires. Age is what judges a lock we cannot probe (a recycled pid, another machine) — and unlike `claims.ts`'s `tokenAbandoned`, a **foreign host is not left alone forever**, because a corpse we may not judge would tax that key permanently and being wrong costs one duplicate compile.
- **Breaking a stale lock is deliberately NOT serialised** with a `.takeover` token. That asymmetry is the whole design: two winners on a device claim means two jobs driving one phone, unrecoverable and misdiagnosed as a regression; two winners here means one duplicate compile — bounded, self-healing (the write is atomic), and exactly today's behaviour. The primitives are shared (`pidAlive`, `writeExclusive`, `tmpPath` are exported from `claims.ts` so the measured write-then-`link` rule has one implementation); the mechanisms are not.
- **Every failure means COMPILE ANYWAY** — unwritable directory, corrupt lock, ceiling reached. `held: false` with no `degraded` is the *disabled* path and prints nothing, so `VERIKUN_NO_PLAN_LOCK=1` restores the pre-lock behaviour exactly, the bisection property `VERIKUN_NO_CLAIM` is held to.
- **ONE LOCK AT A TIME.** `compileFromSegments` takes and releases per iteration, so hold-and-wait cannot arise. Pre-acquiring every segment's lock before the loop looks like an optimisation and **deadlocks**: two tests sharing two fragments enumerate them in different orders. There is a comment at the loop saying so; keep it.
- **`--recompile` still takes the lock** but accepts an entry written after this process started (`cachedSegment`) — a leftover is still ignored, while a lane racing this one right now is not paid for twice. That window is one lane child under a pool and the whole suite when serial; widening it would need the parent to stamp an epoch into `laneEnv`, which is a new concept for a flag that means "do not trust the disk".
- The whole-test key in `obtainPlan` stays unlocked: `vk suite`'s queue is one `shift()` per lane, so no test file is ever in flight twice. The one exception — two files whose *resolved* text is byte-identical — is out of scope and named in a comment.

## Parallel `vk suite` and the `vk server` device pool

Suite wall-clock used to be the **sum** of its tests. Given a pool the suite becomes a work queue, and wall-clock falls to roughly the longest single test. Two halves, shaped by one physical constraint:

**`spawnSync` is why neither half could be a `Promise.all`.** `exec.ts` is synchronous throughout and the whole `Driver` interface sits on top of it, so tests awaited inside one process would still serialize on every adb/idb shell-out. Each device needs its own thread of execution at both ends: a **child process** per test on the client, a **worker thread** per device on the server.

- **Client (`suite.ts` + `cli.ts`).** `suite.ts` imports nothing from `cli.ts`: one FIFO queue, a `laneWorker` per lane. `cli.ts` owns what a lane *runs* (`laneArgv`/`laneEnv` build a `vk ai <file> --json` child, `laneResult` maps its outcome back). The process boundary buys crash isolation, keeps `output.ts`'s `quiet` latch intact, and restores per-test device overrides.
- **Server (`server.ts` + `server-pool.ts` + `server-worker.ts`).** *Every* piece of policy stays on the main thread — auth, the `validateNode` gate, body caps, install streaming — and only the final device call moves to a worker. `DevicePool` is an injected seam (like `ServerLifecycle`), so `tests/server.test.ts` exercises the lease matrix with no device and no thread.

Rules:

- **Affinity needs no new wire field.** The `x-verikun-run` token every remote backend already sends *is* the lease key; `/v1/lease` only lets the client name its device before the first step. Feature-detect on `health.capacity`, never on the version.
- **The reset lives INSIDE the test** (`vk ai --reset-app`): issued from the parent it would take its own lease and could reset one phone and test another. `SuiteDeps.reset` stays wired only on the serial path.
- **The parent holds the device claims as `DeviceGrant`s; children run `VERIKUN_NO_CLAIM=1`** — `isMine` matches on session OR cwd, so siblings would treat each other's claims as their own, and each child's exit would hand its device back mid-suite.
- **An empty queue is not the end while another lane is busy**: a dying lane re-queues its file (the idle poll in `laneWorker`, plus a belt-and-braces `stop` if anything is still queued after `Promise.all`), so no test can end up in no row and no `notRun` list.
- **Lane retirement has two triggers** — a confirmed break (`stillBroken`) or `ENV_STREAK_LIMIT` consecutive environment failures — because a remote preflight can only ping, so one dead device behind a healthy server is caught only by the streak. Pool-only.
- **`install` on a pool goes to EVERY device**, or lanes 2..N silently run the previous build — wrong-but-green. Device-control *mutations* are refused on a pool.
- **Leases and keep-alive.** `server.keepAliveTimeout` equals `LOCK_IDLE_MS` (a client compiling inside `spawnSync` cannot notice a closed socket); a lease is broken **on demand, never on a timer**, survives a failover *decision* (`moving`), and the loser of a takeover is **evicted** (409) rather than re-dealt; `failedOver` records outcomes, not attempts. `othersActive` must exclude idle leases (a crashed client must not block installs forever); `considerFailover` enters the device into `moving` **before its first `await`** and `reapLeases` skips leases on a moving device — `tests/server.test.ts` pins it with a concurrent request inside that window. The measured failures behind each rule: `internals/contracts.md`, *Only the server may repoint the server* and *A pool degrades, it does not shrink*.
- **`--devices` has ONE parser** (`src/device/pool.ts`), shared by `vk server` and `vk suite`; `all` prefers virtual devices over somebody's handset; `--devices` with `--server` is exit 2 (those serials are local).
- **One platform per pool.** A suite dealt onto Android and iOS at once is a matrix, expressed by running it twice; `--servers` refuses a mismatch at exit 2.
- **The plan cache needs no device key, but it does need a LOCK**: `@include` segment keys are shared by every test in a suite, so N lanes compiled the same preamble N times with N different draws — `agent/plan-lock.ts` serialises the per-key compile (see *The plan-compile lock*).

`SuiteTotals.durationMs` keeps its meaning (the sum) and gains `wallClockMs` beside it; serially they are the same number, so anything that prints one must say which it is.

## Unit tests

`npm test` type-checks and runs the suite via **Node's built-in test runner** (`node:test` + `node:assert`) — no test framework is installed, keeping with the zero-runtime-dependency ethos (the only dev deps remain `typescript` + `@types/node`). Tests live in `tests/*.test.ts` and are compiled by `tsconfig.test.json` (extends the base, `rootDir: "."`, `outDir: ".test-build"`, includes `src` + `tests`) into the gitignored `.test-build/`, which `node --test .test-build/tests/*.test.js` then runs. The explicit `*.test.js` glob — rather than passing the bare `.test-build/tests/` directory — is load-bearing on **three** counts: it matches only the test files, so `tests/helpers.ts` (shared `makeEl` / `makePng` fixtures) compiles alongside them but is never run as a test; a single `*` does not cross a directory boundary, so the **device** suite in `tests/e2e/` is type-checked by `npm test` but never *run* by it (see *The Flutter fixture app* below — widening this to `**` would drag device-requiring tests into the device-free CI path and red CI for everyone without a phone attached); and it sidesteps a Node 22 change under which a bare directory argument to `node --test` is import-resolved as a single module (failing with *Cannot find module*) instead of being scanned. The shell expands the glob to explicit file paths, which every Node version runs directly — that is what keeps the suite green on both Node 20 **and** 22 (both are in CI). Keep the glob; don't "simplify" it back to the directory.

**Reporting.** `npm test` uses the `spec` reporter, so the local/CI console shows a readable ✔/✖ list with per-test timings instead of raw TAP. CI runs `npm run test:ci`, which fans the run out to **two** reporters at once: `spec` to stdout (the log) and a custom reporter (`scripts/github-test-summary.mjs`) to `test-results/summary.md`; the workflow then appends that markdown to `$GITHUB_STEP_SUMMARY` so a formatted test list (totals, failures-with-message, and a collapsed list of every test) renders on the Actions run page. The reporter consumes the test runner's **event stream** (real names/messages as plain strings) rather than parsing the built-in JUnit output, whose attribute escaping is lossy for names containing `<`/`>`/quotes (and the suite has such names). It is plain ESM with zero deps **on purpose** — `node --test` loads a reporter module directly, so it can't go through tsc; keep it dependency-free. `test-results/` is gitignored.

Scope is the **platform-agnostic core** — the layers that never touch `adb`/`xcrun`/`idb`, so no device is needed: `args.ts`, `ui/selector.ts`, `ui/android-parse.ts`, `ui/ios-parse.ts`, `ui/format.ts`, `image.ts`, `report.ts`, `errors.ts`, plus pure helpers from `cli.ts`, `commands/`, `run.ts` and `drivers/adb.ts`. A handful of those helpers (`escapeText`, `evalAssert`, `parsePoint`, `healNote`, `stepName`, `rolloverReason`, `grantLanes`) are `export`ed **solely so the suite can reach them** — they are otherwise internal; keep them exported. The `commands/` modules' exports (`parseDuration`, `waitWindowMs`, `waitNote`, `tokenizeLine`, `withBatchGlobals`) are ordinary module exports the suite also imports. The drivers themselves and the `getElements`→`uiautomator` round-trip are intentionally **not** unit-tested (that is what `vk doctor`/`vk ui` against a real device cover). When you add a pure function to the core, add a `tests/<module>.test.ts` case; when you add a platform method, it stays device-verified.

**`tests/docs-coverage.test.ts` is the odd one out, deliberately.** It tests no code — it reads `src/cli.ts` and `src/device/settings.ts` as *text*, extracts the dispatchable commands and the `device set` keys, and fails if any is absent from `reference/commands.md` or `guides/platform-support.md`. It is the enforced half of the docs rule in *Versioning, changelog & docs*: prose asks, this fails CI. It exists because `pages.yml` — the only job that builds the docs and therefore the only thing that validates their links — is **path-filtered to `docs/**`**, so a PR that adds a command and touches no docs file never triggers it, and nothing anywhere noticed. `ci.yml` runs the unit suite on every PR regardless of paths. Aliases come from fall-through `case` labels sharing a handler, so declaring one costs nothing here; the extraction asserts a **floor** on how many commands it found, because a regex that silently matches nothing would make every assertion pass while checking nothing.

## The Flutter fixture app (device e2e)

`example/flutter-app/` is a small Flutter app whose accessibility semantics we control, and `tests/e2e/` drives it through the **built** CLI to pin the machine contract on real hardware. It exists because everything device-side was previously verified against whatever happened to be installed on the tester's phone — `example/example-test.md` used to drive the stock camera and really delete photos. Both `example/*.md` natural-language tests now target this same app (`dev.verikun.testapp`), so the prose tests, the e2e suite and the documented behaviour share one source of truth, and `vk suite example` is a non-destructive gate.

- **`npm run test:e2e` needs a real device and is NOT part of `npm test`.** `VK_E2E_DEVICE=<serial>` for Android, `VK_E2E_PLATFORM=ios` for the simulator. With no device or no fixture installed, the suite skips with a diagnostic rather than failing. `ci.yml` must stay device-free; don't wire this into it.
- **Why a harness rather than `vk batch` or `vk ai`.** `batch` stops at the first non-zero exit and propagates it, so it cannot express *"this SHOULD exit 2"*; `vk ai` heals around precisely the failures worth observing, is nondeterministic, and costs money. `tests/e2e/harness.ts` spawns `dist/bin/verikun.js` and asserts on `{code, stdout, stderr}`.
- **The app is deliberately stateless.** `clearApp` throws on iOS and `vk suite --app` degrades to a force-stop there, so `pm clear` is not a portable reset. With all state in memory, `vk launch` (which force-stops first) is an identical full reset on both platforms. Don't add persistence.
- **`SemanticsBinding.instance.ensureSemantics()` in `lib/main.dart` is load-bearing** — without a held `SemanticsHandle`, Flutter emits no semantics tree at all and `vk ui` sees one empty `FlutterView`. Never dispose it.
- **Every widget wraps in `MergeSemantics`** (`lib/widgets.dart`). A bare `Semantics(identifier:)` emits two sibling nodes — id on one, label and state flags on the other — which made `checked` unobservable on `@vk_remember`. And a node with an identifier but no label survives on Android yet vanishes from the iOS tree entirely.
- **`example/flutter-app/README.md` holds the measured facts** — what `vk` actually reports for each widget, per platform, including two findings that are `vk` gaps rather than fixture quirks: `obscureText` does not set `password` on iOS (so redaction never fires there for Flutter), and a tap issued immediately after `launch` can exit 0 having done nothing. Keep that file measured, not aspirational.
- **`@vk_device` is what makes `vk device set` testable at all.** Its lines come from `MediaQuery` — from the platform, not app state — so a test can assert the app *observed* a device change rather than only that the value landed in a system database. The app's `darkTheme` is load-bearing for the same reason: with only a light theme, `ThemeMode.system` has nothing to switch to and a dark-mode assertion would pass vacuously. A device-settings e2e case must run through the harness's `record: true`, because the snapshot that `device reset` restores from lives in the run file and the suite otherwise sets `VERIKUN_NO_RUN=1`.
- Build with `npm run flutter-app:apk` / `flutter-app:ios`. The SDK is pinned by the committed `example/flutter-app/.fvmrc`; always invoke `fvm flutter`, never bare `flutter`.

## Device settings (`vk device set`)

`vk device set <key>=<value> …` changes the **device** the app runs on — airplane mode, dark mode, font scale, rotation, stay-awake — so a test can exercise offline handling, theming, accessibility text sizes and landscape. `get` / `reset` / `caps` round it out. The design is *snapshot → override → restore*, and four properties are load-bearing:

- **The table is the source of truth** (`device/settings.ts`, above). `cli.ts` never hard-codes a key, a value domain, or a platform gap; it asks the table. The drivers implement a `switch` over `SettingKey` and nothing else.
- **Every write is verified by readback.** `svc`, `cmd`, and `settings put` are all fire-and-forget and are silently ignored on some OEM skins, so trusting the exit code would report success for a change that never happened. `AdbDriver.applyAndVerify` mutates, then polls the setting until it reads the wanted value (200ms × 4s) and throws `CliError(…, 3)` naming both the command and the value still being reported. This is why `Driver` gained a **synchronous** `sleepSync` (`exec.ts`) — the whole `Driver` interface is sync, so a poll cannot await a timer.
- **`airplane=on` is verified by *effect*, not by its flag.** Android keeps `airplane_mode_toggleable_radios` (typically `bluetooth,wifi,nfc`) and remembers a user who re-enabled wifi during a previous flight, so `airplane-mode enable` **can leave wifi up**. `setAirplane` therefore reads `airplane_mode_toggleable_radios` off the device and reconciles only the radios it names — forcing any survivor with `svc` and announcing it on stderr. Deliberately NOT `mobile_data`: cellular is never in that list (the flag cuts it outright), and `mobile_data` is a stored user *preference* rather than live radio state, so on a SIM-less device it keeps reading `1` while the device is plainly offline and would fail a perfectly good offline state. Reporting "offline" while the app is still online would make an offline test pass for the wrong reason — the worst failure mode a testing tool has. Keep that check if you touch it.
- **Restore lives in the run file, not memory.** `RunState.deviceOverrides` maps each key to the value that was live *before* verikun first touched it (earliest wins — setting `dark` twice must still restore to the pre-run value). Because every `vk` call is its own process, an in-memory latch could not undo a flow that died; the run file can, so `vk device reset` works from a later process. `cmdBatch`, `cmdAi` and `cmdSuiteEntry` call it from a `finally`, which is what stops a test that dies between `airplane=on` and `reset` from stranding the device. A bare `vk device set` from a shell deliberately stays applied. **Known gap:** under `--server` the snapshot is written by the *server* process, so a crashed client leaves overrides applied.
- **A rollover must not strand the snapshot.** Because `deviceOverrides` lives in the run and `rolloverReason` *seals* runs, a rollover used to carry the snapshot into the archive while `device reset` — which reads the ACTIVE run — cheerfully reported "nothing to restore". Measured, not theoretical: two workspaces driving different devices from one working directory ping-pong the active run via device-change rollover, and a phone was left dark + rotated with nothing tracking it. `beginStep` now carries unrestored overrides **forward** on a same-device rollover, and on a device-change rollover warns loudly with the exact `vk device set … --device <serial>` needed to undo it (it cannot drive the old device from a process pointed at the new one, and restoring one device's values onto another would be worse than leaving it). `tests/run-device-overrides.test.ts` pins both paths.

Two guards worth preserving. `adbTransport(serial)` classifies a serial as `usb`/`tcp`/`emulator`, and `severanceRisk` refuses `airplane=on` over a **wireless adb** link (exit 2, `--allow-wireless` overrides) — it would cut the very channel carrying the next command, and recovery means physically plugging in USB. An unrecognized serial shape deliberately falls back to `usb`: this is a foot-gun net, not a security boundary, so blocking a legitimate run is the worse error. And `validateNode` checks a `device` leaf's keys/values at **plan-validation time**, unlike every other command (whose selector failures are runtime facts the engine can heal) — that is what makes a `vk suite` asking for `rotation` on iOS fail before the first tap rather than on a half-modified device.

Every device token issued comes from the table's closed enum, so no caller-supplied string reaches the device shell and no `assertSafeAppId`-style gate is needed — which is also why `device` is safe to expose over `vk server` RPC without a new `--allow-*` flag (unlike `install`, which writes an arbitrary binary).

## Server device failover (`src/device/failover.ts`)

One bad device used to wedge every job on a `vk server` host while healthy devices sat idle (issue #99). Failover lets the **server** move itself off a device that fails. `src/device/failover.ts` is PURE (classify a string, filter a list — no fs, no spawn, no Driver); the probing, claiming and rebinding live in `server.ts`'s `buildServer` closure.

- **The install classifier enumerates the FILE, not the device — that polarity is the design.** The file-attributable set (`INSTALL_PARSE_FAILED_*`, `INSTALL_FAILED_INVALID_APK`, `_TEST_ONLY`, an unreadable upload) is small and closed; the device side is open-ended and OEM-specific, so `ARTIFACT_RULES` is the only brake and everything else moves, including wordings nobody has met. The named `DEVICE_STATE_RULES` are a fast path, never the gate; `tests/failover.test.ts` pins that by feeding the classifier gibberish that must still move.
- **`exec`/`elements` keep the OPPOSITE default** — stay unless the device is unreachable or a two-probe re-check (`deviceIsDead`, the same shape as `suite.ts`'s `stillBroken`) confirms it dead, because exit 3 there is dominated by transient noise. `probe: false` on `transient`/`toolchain` is load-bearing (a device mid-`launch --clear` fails a probe; with adb missing *every* probe fails), and the probe's **own** error is classified the same way (`deviceIsDead`).
- **A step is NEVER replayed on the new device.** Only `install` retries; everything else rebinds and returns the **original** device's error — replaying step 12 on a device that never ran 1–11 is a false green or a repair against the wrong hierarchy. On exhaustion the client gets the FIRST device's error, which is what makes move-by-default safe.
- **ON BY DEFAULT, off when `--device` is pinned** (`parseFailover`); `--allow-failover[=serials]` re-enables and bounds it, `--no-failover`/`VERIKUN_NO_FAILOVER` is the kill switch, announced at startup. `allow-failover` stays OUT of `args.ts`'s `BOOLEAN` set (its `=value` form is the point); `no-failover` belongs in it.
- **The claim moves with the binding: claim-new → probe → commit → release-old.** A candidate another job holds is skipped, never quarantined. `buildServer` takes a `claimOpts` test seam so a unit test never writes into `~/.verikun/devices`.
- **Failover never boots** (`failoverCandidates` drops `serial: ''`) — lateral, never upward; booting is `vk devices start --server`'s job.
- **On a pool: demote, never shed; the lease follows the move; no quarantine TTL; reconcile once a minute; bound every worker call.** `pickFailoverDevice` excludes every current pool member and `pool.adopt(next)` runs *before* `pool.retire(failed)`, with **no `await` between them**, so the lease remap lands in the gap; a demoted device keeps its slot and is dealt last (`leaseFor` deals healthy-first, then least-recently-used); recovery is proven by traffic (`restoreDevice`), never by a clock; `reconcileOnce` re-adopts what `--devices` asked for (`all` re-enumerates; an explicit list never grows beyond its serials), installing `lastInstall` first — it is skipped while `exclusive` is held, runs through `serializeFailover`, and its timer is `unref`'d and cleared on `server.close`; a quarantine (`failedOver`) is cleared only by a successful `/v1/devices/*` (refused on a pool, `requireSingleDevice`) or by rejoining the pool; `WORKER_CALL_TIMEOUT_MS` terminates a wedged worker so the sweep can replace it. iOS gets the probe arm only (`idb install` failure strings are unmeasured). Each rule's postmortem: `internals/contracts.md`, *A pool degrades, it does not shrink*.

## Device claims and grants (`src/device/claims.ts`, `src/device/grant.ts`)

Which attached device is another job already driving? Parallel agents in separate worktrees share one pool of phones, and without coordination two jobs land on one device and **both** die as ordinary-looking assertion failures (issue #49). A claim is one small JSON file per serial under `~/.verikun/devices/` — host-global, because a device is a fact about the *machine*, not about a working directory. The mechanism and its measured races (write-then-`link()`, the `<claim>.takeover` token, pid-plus-TTL liveness): `internals/contracts.md`, *Device claims: acquire exclusively, prove liveness*. `tests/device-claims.test.ts` gates the takeover token deterministically; the multi-process race tests in the same file only detect it **under load**, so don't treat them as the gate.

- **Selection and acquisition are one step**: `selectAndClaim` / `assertClaimable` run inside `resolvedSerial()` in both drivers (or two agents starting together both take device #1). The heartbeat (`touchClaim`) runs from `executeOutcome` + `executeForServer` in `cli.ts` — not from the memoized `resolvedSerial()`, and **outside** the recorder branch, because `beginStep` returns null under `VERIKUN_NO_RUN=1`, which the e2e suite sets.
- **A live pid always means live; a dead pid means done only for `processScoped` owners** (`ai`/`suite`/`batch`/`server`, via `setProcessScoped()`); a one-off `vk tap` falls back to the idle TTL (`VERIKUN_CLAIM_TTL_MIN`, default 5). `PID_TRUST_MAX_MS` caps pid trust.
- **Ownership matches on session OR cwd** (`isMine`): the only unsafe error is accusing your own job.
- **Never a new way to fail.** Corrupt claim → unclaimed; unwritable store → log and continue. `VERIKUN_NO_CLAIM=1` disables reads *and* writes and restores the pre-claims behaviour **exactly** (including exit 2 on multiple devices) — keep that equivalence. No `--force` flag, deliberately; `vk device release` is the break-glass named in every refusal.
- **`pidAlive`, `writeExclusive` and `tmpPath` are exported for ONE other consumer**, `agent/plan-lock.ts`: the two mechanisms stay separate (different trust domains), the primitives do not, because a second `pidAlive` fails invisibly.
- **A `DeviceGrant` is the shared lifecycle** — take a device, keep it warm, hand it back — over either a host claim or a server lease (`ResolvedBackend.grant`; `cmdSuiteParallel` holds one per local lane). Claims and leases stay **separate implementations** (different trust domains); idle takeover, eviction and affinity are pool policy and live only in the server.
- **Two acquisition polarities are the whole grant API**: `claimGrant` returns `null` for a device somebody else holds (`--devices all` asked for a *set*), `requireClaimGrant` throws exit 2 (a named serial must not be dropped silently). The `VERIKUN_NO_CLAIM` gate lives in the constructors, and with claims off `claimGrant` still returns a grant — never `null` — because nothing can tell it a device is busy; `touch` is a no-op wherever something truer already stamps the claim, and the one timer (the parallel-suite parent) takes its period from `claimHeartbeatMs`, derived from `claimTtlMs` (a quarter, 5s–60s) so the two cannot drift; `release` is idempotent and `releaseGrants` never short-circuits.
- **`vk install` deliberately keeps its local claim** (`backend.close?.()`, not `grant.release()`) so `vk install && vk suite` bridges the two commands. A `vk server` worker cannot use a grant (acquired on the worker thread, released from the main thread) and calls `claims.ts` directly.

## Extending a platform backend

To add a capability, add the method to the `Driver` interface in `types.ts`, then implement it in **both** drivers. iOS is `IdbDriver` (`drivers/ios.ts`): it shells to `xcrun simctl`/`devicectl` for discovery and — on a simulator — screenshots/launch/stop/logs, and to Facebook's **`idb`** for the accessibility hierarchy (`idb ui describe-all` → `ui/ios-parse.ts`), all interaction (`idb ui tap/text/swipe/key/button`), screen size (`idb describe`), and lifecycle on physical devices. A private `isSimulator()` (is the resolved UDID in `simctl list`?) picks simctl-vs-idb for the branchable methods; `resolvedSerial()` must return a **concrete UDID** (idb can't address the simctl-only `booted` alias). Two methods have no clean iOS equivalent and **degrade honestly** rather than half-implement: `clearApp` throws `CliError(…, 3)` (no per-app data reset) and `currentApp` returns `"(unknown)"` (no foreground query) — keep that shape for any similar gap.

**Device lifecycle is a SECOND, device-unbound seam** (`drivers/lifecycle.ts`), deliberately *not* part of `Driver`: every `Driver` method funnels through `resolvedSerial()`, which throws exactly when no device is attached — precisely the state in which you want to boot one (and `Driver.stop(appId)` already exists, so a `Driver.stop(deviceName)` sibling would be a permanent reader trap). `DeviceLifecycle` addresses targets by **name** (AVD name / simulator name), dispatches to module-level functions in `adb.ts`/`ios.ts`, and carries the pure `chooseTarget` (the exit-2 ambiguity contract — simulator names repeat across iOS runtimes, so `iPhone 17 Pro` alone is genuinely ambiguous) and `assertActionable` (the `--wipe` guardrails). Lifecycle verbs are **not** in `KNOWN_COMMANDS` and **not** `RECORDABLE`: they are environment management, and adding them to that set would let a `vk ai` repair "fix" a failing step by rebooting the device.

**Boot waits are async poll loops of SHORT `spawnSync` probes** (`wait.ts`'s `pollUntil`), never one blocking `simctl bootstatus -b` / `adb wait-for-device`. A 2-minute blocking spawn freezes the event loop, and inside `vk server` that means `/v1/health` goes dark for the whole recovery while the device lock's idle-takeover clock keeps running. Readiness must mean **drivable**, not *powered*: on iOS, gate on `simctl bootstatus` — measured on a cold sim, simctl reports `Booted` (and `simctl getenv` succeeds) ~1s in, but `idb ui describe-all` returns a stub 1-node tree until bootstatus exits at ~6s, so gating on state alone hands back a device whose screen reads as *empty* rather than as *not ready*: a false green. `exec.ts`'s `spawnDetached` and `spawnCollect` are the only non-`spawnSync` paths (the emulator must outlive the CLI; the parallel suite must not block on its children). `spawnDetached`'s stdio must never be `inherit`/`pipe`, or the emulator holds the CLI's stdout open and a caller capturing `vk`'s output never sees EOF.

`vk server --allow-device-control` is the remote face of the same seam, and the only thing a **client** can use to change the server's device binding (`/v1/exec` never can; the **server** may also move itself — see *Server device failover* below). It is two-tier — bare = restart/stop the bound device; `=<names>` = also start from that operator-declared allowlist — because enumerating the host's AVDs is autocomplete, not authorization. With the flag the server may also listen with **no device bound** (deferring `resolvedSerial()`, `503` on device endpoints) — but only for exit-3 "no device"; an exit-2 *ambiguity* is an operator error and still fails fast. Rebinding rebuilds the driver via `getDriver(platform, <concrete serial>)` rather than invalidating a cache, because `AdbDriver` caches both its resolved serial and a pinned `requested` without probing.

`AdbDriver.install()` **replaces a differently-signed build rather than failing** (issue #96). Android will not update a package across signing keys, and until 0.26 nothing in vk could clear that: `clear` wipes data, not the certificate, and over `--server` there is no shell to run `adb uninstall` from — so one stale build stranded the device and every CI run against it. Three properties are load-bearing. It replaces **on failure, never up front**, because with the same key `-r` keeps app data and that has to stay lossless; data is destroyed only where the install would otherwise have failed outright, which is why this needs no opt-in flag and no separate permission (`--allow-install` already authorizes writing an arbitrary binary to the device). The package name comes from **adb's own failure message** — `aapt dump badging` needs build-tools that may be absent and decoding a binary AndroidManifest is out of the question here — and `blockingPackage()`'s pattern **is** the safety gate: it can only yield `[A-Za-z0-9._]+`, and it anchors on the trailing `signatures do not match` so a stray character fails the whole match instead of yielding the prefix before it. Naming no package is safe (install stops and says so); naming the wrong one would uninstall an app nobody asked about. And the removal is **announced on stderr**, because it is destructive and nobody asked for it in so many words.

`AdbDriver.launch()` resolves the app's default LAUNCHER activity with `cmd package resolve-activity --brief` and starts it with `am start -n <component>`. It deliberately does **not** use `monkey -c LAUNCHER`: monkey hangs indefinitely on some OEM skins (e.g. MIUI/HyperOS), tripping the exec timeout. If you touch launch, keep the `am start` path.

`cmdLaunch` (the `launch`/`open` command, not the driver primitive) **restarts by default**: it force-stops the app *before* `driver.launch()`, because re-issuing the launch intent to an already-running/foregrounded app just resurfaces its current (often mid-flow, stale) screen rather than starting fresh — which is what made reruns flaky. force-stop is a no-op when the app isn't running, so no "is it running?" probe is needed (and none would be portable — the iOS backend has no foreground query). `--no-restart` opts out (bring the existing instance forward); `--clear` instead wipes data via `pm clear` (which already force-stops).

## The server log (`src/server-log.ts`)

`vk server` is a long-lived process an operator reads about later, and its diagnostics used to go to stderr and nowhere else. The file is on by default at `~/.verikun/logs/server-<port>.log`, named in the startup banner.

- **The tee lives in `err()`** (`output.ts`'s `setErrSink`), which also captures the worker threads' forwarded stderr. Deliberately NOT on `out()`: stdout is the data channel, and a sink there would tee a `--json` payload into a log.
- **`--log-file <path|off>` — one flag whose VALUE is the switch** (`VERIKUN_LOG_FILE` likewise). No `--no-log-file`, because **`--no-logs` / `VERIKUN_NO_LOGS` already means something unrelated** (skip device-log capture on a green archive). `log-file` stays OUT of `args.ts`'s `BOOLEAN` set, and a bare `--log-file` is exit 2.
- **Host-global and port-scoped**, like the claim store. **Never a new way to fail**: an unwritable path warns and continues stderr-only, the sink's own throw is swallowed inside `err()`, and a failed rotation (10 MB → one `.1`) keeps appending. Timestamps go in the file only, so stderr stays byte-identical for the tests.

## The version check (`src/update-check.ts`, surfaced by `vk doctor`)

Is this `vk` behind npm's `latest`, and is the installed Claude Code plugin's `SKILL.md` behind this `vk`? The second is the one that bit (issue #59). **It lives only in `vk doctor`** — an explicit "check my setup" — so there is no cache, no snooze and no separate command.

- **No probe here ever fails doctor**: they are `ok: true` with `ToolProbe.advisory` set, rendered on stderr with a hint but never touching the exit code. Out of date is not a broken machine, and a firewalled CI box must not go red.
- **Everything degrades to silence**: `updateProbes` returns `[]` on any error; comparison is release-only and an unparseable side yields no opinion (the plugin registry really contains `"unknown"` and bare-SHA versions). The registry is parsed defensively (its own top-level `version` is ignored) and `CLAUDE_CONFIG_DIR` is honoured, which is also how this is tested.

## Repo doubles as a Claude Code plugin

- `.claude-plugin/marketplace.json` + `.claude-plugin/plugin.json` make this repo installable as a marketplace plugin (`source: "./"`). Validate manifest changes with `claude plugin validate .`.
- The plugin ships the **skill** at `.claude/skills/verikun/SKILL.md` (referenced via the manifest's `"skills": "./.claude/skills/verikun/"` — not moved or duplicated). That SKILL.md is the agent-facing contract: the act→inspect→assert loop, selector grammar, exit-code semantics, the "prefer textual hierarchy lookups over screenshots to save tokens" guidance, and the convention of remembering semantic identifiers across runs. It is one of the three things a behaviour change must update — see *Versioning, changelog & docs* above for the canonical rule, and *Documentation site* below for which `docs/` page owns which contract. SKILL.md is the copy an agent reads at runtime, so a stale line here does not merely misinform a human: it makes the agent drive the device wrongly.
- **`skills` lists one entry per shipped skill — never the container, and never just one.** The field takes *directories* and only ever **adds** to the scan; there is no way to subtract. Claude Code loads an entry as a single skill when that directory holds `SKILL.md` directly, and otherwise scans it for `<name>/SKILL.md`. So `./.claude/skills/` published **every** skill in it, contributor-only `create-pr` included, up to and including 0.19.0 — while naming a single skill silently drops `suggest-verikun-improvement`, which `SKILL.md` hands off to. The array form excludes exactly `create-pr`. `tests/plugin-manifest.test.ts` derives the expected set from `metadata.internal: true` on disk rather than hard-coding names, so adding a skill fails the test until the manifest is updated.
- **`package.json`'s `"files"` is an allowlist, and it is load-bearing.** npm force-includes only five things — `package.json`, `README*`, `LICENSE`/`LICENCE` (either spelling, any case or extension), the `main` file and the `bin` file(s) — **not** `CHANGELOG.md`, not the skill; this bullet is the **canonical** copy of that list (`tests/package-files.test.ts` points here rather than restating it). Everything else must be named there, or it is silently absent from the tarball while `npm publish` succeeds. Name the skill **file**, never the `.claude/skills` directory (`create-pr` is contributor-only), and keep `example` as the glob **`example/*.md`** (a bare directory sweeps the whole Flutter fixture in). Two guards at two levels: `tests/package-files.test.ts` asserts the allowlist (**intent**) and `scripts/check-package-contents.mjs` packs the tarball and asserts its contents (**result**) — run it after any packaging change; it also gates `ci.yml` and `publish.yml`. If you change what ships, update both. The full reasoning: `internals/contracts.md`, *Packaging: `"files"` is an allowlist*.
- Non-Claude agents install the skill via [`vercel-labs/skills`](https://github.com/vercel-labs/skills) (`npx skills add ddikman/verikun --skill verikun`), which reads any `SKILL.md` with `name`/`description` frontmatter straight from the repo. `create-pr` carries `metadata.internal: true` so that tool hides it from end-user installs (it's contributor-only); Claude Code ignores the key.

## Documentation site (`docs/`)

An **Astro Starlight** site published to GitHub Pages at <https://ddikman.github.io/verikun/> by `.github/workflows/pages.yml` (push to `main` touching `docs/`; a PR builds it as a check without deploying). `package.json`'s `homepage` points at it.

```sh
npm run docs:install         # = npm ci --prefix docs; needs Node >= 22.12 (Astro 7), the repo's own CI still runs 20.x + 22.x
npm run docs                 # = npm run dev --prefix docs; http://localhost:4321/verikun/ (bare localhost:4321 is a 404)
npm run docs:build           # = npm run build --prefix docs; production build — FAILS on a dead internal link
```

- **A separate npm project, deliberately**: `docs/package.json` with its own lockfile and no root `workspaces` key. Astro never moves into root `devDependencies` — the zero-dependency rule governs the published CLI, the site's tree is its own — and nothing under `docs/` ships to npm. If a docs entry ever joins `"files"`, note that `check-package-contents.mjs` substring-matches `create-pr`/`changelog-entry` on the whole path and `tests/package-files.test.ts` only understands `<dir>/*.<ext>` globs.
- **`base: '/verikun'` in `astro.config.mjs` is load-bearing** (a *project* Pages site); internal links are absolute `/verikun/...` paths. **`starlight-links-validator` fails the build on a dead page link or anchor** — keep it.
- **Diagrams render client-side** via `src/components/Mermaid.astro` (never `rehype-mermaid`, which would pull a browser into every docs build; keep its `<pre>` fallback so a broken diagram cannot blank a page). `docs/pr/` and `docs/screenshots/` are PR-description assets that predate the site — don't move them.
- **Which page owns which contract** — update these alongside `SKILL.md`/`README.md`:

  | You changed | Update |
  |---|---|
  | a command or flag | `reference/commands.md` |
  | selector rules / state modifiers | `reference/selectors.md` |
  | auto-wait or auto-scroll | `reference/auto-wait.md` |
  | an exit code | `reference/exit-codes.md` |
  | an env var | `reference/environment-variables.md` |
  | report/run/suite-manifest shape or rollover | `reference/reports-and-test-runs.mdx` |
  | a `device set` key | `reference/device-state.md` |
  | the `vk ai` grammar, IR or model list | `reference/ai-plans.md` + `internals/plan-ir-and-engine.md` |
  | the cost mechanism, the estimate formula, or a budget flag | `reference/cost.md` |
  | a cross-cutting invariant | `internals/core-principles.md` + `internals/contracts.md` |
  | device claims, grants or leases | `reference/device-claims.md` + `internals/contracts.md` |
  | **a platform gap, an honest degrade, or anything that differs simulator-vs-device** | `guides/platform-support.md` |
  | parallel suites / the server device pool | `guides/suites.mdx` + `guides/remote-devices-and-ci.md` |
  | the version check | `getting-started/installation.md` |

  `reference/ai-plans.md` deliberately describes the grammar's **concepts** and links to `src/agent/grammar.ts` + `SKILL.md` rather than pasting the prompt text — the prompt is a runtime artifact with a cache fingerprint attached, and a verbatim fourth copy is a liability.

  `guides/platform-support.md` is the **canonical** platform matrix — commands, selectors/state modifiers, `device set` keys and reporting features, each split Android/iOS × physical/virtual. It exists because those facts had drifted across nine places in three shapes (and the selector-portability table existed verbatim twice). The pages that used to carry a partial copy — `guides/ios-setup.md`, `reference/device-state.md`, `guides/troubleshooting.md`'s iOS table — now link to it, so a new gap is documented **there** and referenced elsewhere, never restated. Its tables are **raw HTML**, because a GFM table cannot express the grouped `colspan` header; that means no markdown inside them, and — load-bearing — **no links inside them either**, since `starlight-links-validator` walks the mdast and never sees an `<a href>` in a raw HTML block. Keep cross-links in the prose around each table where the build can still check them.
